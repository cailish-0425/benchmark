# 评测集设计框架

将评测项目信息转化为三件套输出：
1. 数据集构建三原则（数据集长什么样）
2. 4~6 个一级维度 + 对应二级维度 + 打分规则（怎么打分）
3. 5~8 道 case 样例（好答案 vs 坏答案）

---

## 适用场景

- 正在设计一个新的评测集，需要系统化方法论
- 已有评测数据但维度混乱、打分标准不统一
- 需要把打分规则做得可执行，让标注员不靠主观判断
- 想从已有 case 反推评测框架
- 需要向团队或领导解释评测集的设计逻辑
- 多个评测项目需要统一的标准化流程

## 使用方式

用户会提供评测项目的背景信息，你需要按六步流程输出完整的评测方案。

**输入：** 评测项目信息（评测什么、数据来源、被评测对象、用途、难点等）
**输出：** 构建三原则 + 一级维度 + 二级维度 + 打分规则 + case 样例

用户可能以完整信息启动，也可能只给零散描述。不论哪种，都从第一步"收集信息"开始，识别缺口后追问。

## 第一步：收集输入信息

### 需要什么

**必填（缺一不可）：**

| 编号 | 问题 | 说明 |
|------|------|------|
| A1 | 评测什么能力？ | 一句话描述 |
| A2 | 被评测对象？ | 模型/系统名称 |
| A3 | 评测结果用途？ | 内部研究 / 产品决策 / 模型选型 |
| B1 | 数据怎么来的？ | 线上打捞 / 手工构造 / 爬取 / 合成 |
| B2 | 数据覆盖的时间范围？ | 影响 case 时间锚点，必须有 |
| B3 | 数据规模？ | 大概多少题 |

**选填（有则更好）：**

| 编号 | 问题 |
|------|------|
| C1 | 最难的地方是什么？ |
| C2 | 模型最容易在哪出错？ |
| D1 | 人工标注 / 模型打分 / 混合？ |
| D2 | 专职标注员还是出题人自己标？ |
| E1 | 已有维度草稿 |
| E2 | 已有 case 例子 |
| E3 | 对标行业评测集 |

### 怎么收集

**三条铁律：**
1. 对话里已出现的信息直接用，不重复问
2. A1 和 B2 缺失时必须问，不能假设后继续——这是最严重的错误
3. 先一次性列出所有待确认问题，再按优先级渐进追问

**追问优先级：**
- P1（没有不能继续）：A1、B2
- P2（强烈建议）：A3、B1、C2、D1
- P3（有更好）：C1、D2、E1~E3

P1 用户说"不清楚"→ 引导推导，不能跳过。
P2/P3 用户说"不清楚"→ 标注"待确认"后继续。

### 信息不足时的兜底策略

- 用户坚持说"不清楚"且无法引导推导：输出当前信息下的方案草稿，明确标注哪些结论受限于信息缺失，建议补充后重新评审
- 用户只给了零散描述没有按表格填：从描述中自动提取已确认的信息，只追问真正缺失的必填项
- 用户给了大量背景但没有结构化：先自行整理为结构化摘要，确认后再继续

### 输出

一份结构化的项目信息摘要，标注哪些已确认、哪些待确认。

## 第二步：推导数据集构建三原则

### 需要什么

第一步收集的项目信息。

### 做什么

按固定框架推导三个原则。**框架固定，内容随项目变化。**

```
原则一：模型陌生的     → 规避记忆优势，测真实泛化
原则二：种类足够丰富   → 保证覆盖面，结论普适
原则三：有明确难度梯度 → 画出能力曲线，而不只是一个总分
```

**每个原则输出三样东西：**
1. 一句话定义：解决什么问题
2. 具体做法：数据集怎么操作
3. 2~3 个具体 case：必须有时间锚点 + 真实库/API 名 + 失败模式

**各原则要点：**

原则一（模型陌生的）：
- case 时间必须在项目启动之后，训练截止之前的内容无效
- 指向真实存在的库/API，不编造
- 说清楚"模型为什么会在出错"的具体机制

原则二（种类足够丰富）：
- 在三个子维度上展开：输入类型、问题类型、领域类型
- 每个子维度举 2~3 个例子

原则三（有难度梯度）：
- Easy：单一信息源 + 单步推断
- Medium：多信息源 + 两步推断
- Hard：多约束 + 多步推断 + 信息缺口（三个条件同时满足）
- 难度分档的价值：不是让题有难有易，而是画出能力曲线

### 自检

- [ ] 三个原则描述的是"数据集长什么样"，不是"模型能力如何"
- [ ] 每个原则有 2~3 个带时间锚点的 case
- [ ] case 中的库名、API 名、时间真实存在，没编造

## 第三步：确定一级维度

### 需要什么

第一步的项目信息 + 第二步的构建原则。

### 做什么

根据项目实际情况，分析并提出 4~6 个一级维度候选方案，供用户确认或调整。

#### 分析流程

**（1）从项目信息中提取考察方向**

回答以下问题：
- 这个评测项目最核心要测的是什么能力？
- 被评测对象最可能在哪些方面出错？
- 评测结果的用途（研究/决策/选型）决定了哪些维度是关键的？

**（2）匹配考察层次**

默认使用四层框架（如项目不适合，可自行定义标签，但必须满足三条规则）：

```
感知层   → 读没读对？    （模型能不能读准输入信息）
理解层   → 问没问对？    （模型能不能理解用户意图）
执行层   → 条件全满足？  （模型能不能按要求完成任务）
可信度层 → 知不知道不确定？（模型知不知道自己的推断边界）
```

**（3）生成候选方案**

每个一级维度候选需要包含：

```
【维度名称】
【考察层次】感知层 / 理解层 / 执行层 / 可信度层（或其他自定义标签）
【核心问句】用一个独立问句检验这个维度在测什么
【为什么选它】从项目信息出发，说明为什么这个维度是必要的
【不选的风险】如果去掉这个维度，会漏评什么
```

**（4）呈现给用户**

用以下格式输出候选方案，让用户确认：

```
基于你的项目信息，我建议以下 X 个一级维度：

维度一：[名称]（[层次]）
  → 考察：[核心问句]
  → 必要性：[为什么选它]
  → 不选的风险：[会漏评什么]

维度二：[名称]（[层次]）
  ...

请确认是否需要调整：
- 增加维度（告诉我你想考察什么）
- 删除维度（告诉我为什么不重要）
- 修改维度（告诉我哪里不对）
```

#### 三条规则（确认后必须满足）

**规则一：每个维度有唯一的"考察层次"标签**

两个维度用同一个层次标签 → 有交叉，必须合并或重新定义。

**规则二：每个维度用一个独立问句检验**

两个维度的检验问句高度相似 → 它们在测同一件事，需要合并。

**规则三：构建原则 ≠ 评测维度**

判断标准：
- "我们选了哪类数据" → 构建原则，不是维度
- "我们考察模型什么能力" → 维度

如果维度描述里出现大量"我们选了…""我们覆盖了…" → 构建原则混进来了，剥离。

**维度数量参考：**
- 单模态单任务：4 个
- 多模态或多任务：5 个
- 多模态 + 多任务 + 多约束：6 个

### 标准维度池（按需选用）

| 维度 | 层次 | 适用场景 |
|------|------|----------|
| 输入信息提取准确性 | 感知层 | 视觉/文档输入 |
| 用户意图理解与对齐 | 理解层 | 问答类评测 |
| 复杂约束遵循度 | 执行层 | 多条件任务 |
| 回答的边界意识 | 可信度层 | 信息可能不完整 |
| 多步推理连贯性 | 执行层 | 链式推断 |
| 跨域知识迁移稳定性 | 理解层 | 多语言/多领域 |

### 自检

- [ ] 每个维度有明确的考察层次标签，且不重复
- [ ] 相邻维度的检验问句不同
- [ ] 维度描述里没有"我们选了…"这类构建原则的内容
- [ ] 每个维度都有"为什么选它"和"不选的风险"
- [ ] 用户已确认维度方案（或已标注待确认）

## 第四步：拆分二级维度

### 需要什么

第三步确认的一级维度 + 项目信息 + 构建原则。

### 做什么

将每个一级维度拆分为 2~4 个二级维度。每个二级维度需要：评判标准 + 拆分理由。

#### 拆分原则

**（1）每个二级维度考察一级维度的一个独立侧面**

- 二级维度之间不能有交叉（A 的好坏不影响 B 的判断）
- 所有二级维度加起来要能完整覆盖一级维度

**（2）二级维度必须落到可评判的粒度**

- 不能是"回答质量好不好"这种笼统描述
- 必须是"关键信息点是否提取完整""约束条件是否逐一满足"这种可数、可查的

**（3）每个二级维度都要有评判标准**

不是打分规则（那是第五步），而是定性标准：什么算好、什么算不好。

#### 输出格式

每个一级维度按以下结构展开：

```
## 一级维度：[维度名称]（[考察层次]）

### 二级维度拆分

#### [二级维度名称 1]

**评判标准：**
- 好的标准：[具体描述什么情况算做得好]
- 不好的标准：[具体描述什么情况算做得差]
- 判断依据：[标注员根据什么来判，必须是可观测的]

**拆分理由：**
- 这个二级维度考察的是一级维度的哪个侧面
- 为什么需要单独考察（和同级其他二级维度的区别）
- 不拆分会导致什么问题

#### [二级维度名称 2]

**评判标准：**
- 好的标准：...
- 不好的标准：...
- 判断依据：...

**拆分理由：**
- ...

（每个一级维度拆 2~4 个二级维度）
```

#### 完整示例

以"用户意图理解与对齐"（理解层）为例：

```
## 一级维度：用户意图理解与对齐（理解层）

### 二级维度拆分

#### 问题类型识别

**评判标准：**
- 好的标准：准确判断用户是在问"是什么"还是"怎么做"还是"为什么"
- 不好的标准：把"怎么做"的问题回答成"是什么"的定义
- 判断依据：对比用户 query 的真实意图和模型回答的结构类型

**拆分理由：**
- 这是理解层最基础的能力——连问题类型都判断错，后面一定错
- 和"关键信息定位"不同：前者是读对问题，后者是读对输入
- 不单独拆分的话，标注员会把"读错了输入"和"理解错了意图"混在一起打分

#### 关键信息定位

**评判标准：**
- 好的标准：从输入中准确找到回答问题所需的全部关键信息
- 不好的标准：遗漏了关键信息，或提取了无关信息
- 判断依据：对照"关键信息点清单"逐条核查是否被提及

**拆分理由：**
- 这是理解层的输出能力——理解了意图之后，能不能找到支撑回答的信息
- 和"问题类型识别"互补：一个管"问没问对"，一个管"找没找到"
- 不拆分的话，模型"理解对了但找错了信息"的情况会被混为一谈

#### 需求完整性判断

**评判标准：**
- 好的标准：识别出用户隐含的需求（用户没说但需要的）
- 不好的标准：只回答了字面问题，忽略了上下文中的隐含需求
- 判断依据：回答是否覆盖了"用户应该会关心但没明说"的点

**拆分理由：**
- 这是理解层的高阶能力——不只是理解说了什么，还要理解没说什么
- 和前两个二级维度形成递进：类型识别 → 信息定位 → 需求补全
- 不拆分的话，"理解了字面意思但没理解深层需求"的情况无法被评估
```

#### 各层次常见拆分模式

以下为参考，按实际情况选用或自定义：

**感知层常见二级维度：**
- 关键信息提取完整性（该读的读全了吗）
- 信息识别准确性（读对了吗，有没有看错）
- 噪声信息过滤（不该信的没信吧）

**理解层常见二级维度：**
- 问题类型识别（问的是什么类型的）
- 关键信息定位（从输入中找到了什么）
- 需求完整性判断（隐含需求识别了吗）

**执行层常见二级维度：**
- 硬约束满足度（必须做到的做到了吗）
- 软约束满足度（建议做到的做到了吗）
- 输出格式合规性（格式要求满足了吗）

**可信度层常见二级维度：**
- 不确定性识别（知道哪里不确定吗）
- 影响范围说明（说清楚了不确定会怎么影响结论吗）
- 方向性推断质量（给了有价值的推断方向吗）

### 自检

- [ ] 每个一级维度拆了 2~4 个二级维度
- [ ] 同一级维度下的二级维度之间不交叉
- [ ] 所有二级维度加起来能完整覆盖一级维度
- [ ] 每个二级维度都有"评判标准"和"拆分理由"
- [ ] 评判标准是可观测、可判断的，不是笼统描述
- [ ] 拆分理由说清了"为什么单独考察"和"不拆分的问题"

## 第五步：生成打分规则

### 需要什么

第四步的二级维度 + 项目信息。

### 做什么

将第四步的定性评判标准转化为可操作的打分规则。核心要求：**标注员不靠主观判断，直接执行。**

#### 出题表模板（每道题必填）

```
【题目ID】
【输入描述】
【用户问题】
【参考答案】
【关键信息点清单】（编号列出）
【约束条件列表】（编号列出，无则填"无"）
【信息缺失标记】（是/否）
【难度档位】Easy / Medium / Hard
```

#### 打分规则速查表

按一级维度的考察层次选择对应模板，为每个二级维度编写打分规则：

**感知层 — 逐条核查信息点**
```
最小单位：关键信息点（可数）
结果：✓ 正确（与原始一致） / ✗ 错误（不一致或未提及）
得分：正确数 / 总数
```

**理解层 — 整题三档**
```
2分：区域对齐正确 + 问题类型识别正确
1分：一对一错
0分：两个都错，或与输入无关
边界：与输入有实质关联，最低 1 分
```

**执行层 — 逐条核查约束**
```
最小单位：约束条件（可数）
结果：✓ 满足(1) / △ 部分满足(0.5，仅可量化约束) / ✗ 违反(0)
得分：(满足数 + 部分满足数×0.5) / 总约束数
区分：硬约束（只有✓/✗）vs 软约束（允许△）
```

**可信度层 — 仅对信息缺失题打分**
```
触发：信息缺失标记=是 的题才打分，其余默认满分
2分：指出缺失 + 说明影响 + 给方向性推断
1分：识别到不足但模糊，或直接拒答
0分：未识别不足就给确定性答案
0分信号："一定是""肯定是""就是因为" + 指向缺失部分
```

#### 权重分配

```
一级维度权重（参考）：
感知层：15~20%（基础门槛）
理解层：25~30%（核心）
执行层：25~30%（核心）
可信度层：15~20%（拔高）

二级维度权重：
每个一级维度下的二级维度权重由均分起步，
根据重要性差异调整，总和等于该一级维度的权重。
```

以上为参考范围，按项目实际情况调整，所有权重总和必须为 100%。

### 自检

- [ ] 感知层和执行层的打分单位是"可数的"（信息点数、约束数）
- [ ] 理解层有明确的 0/1/2 分判断边界
- [ ] 可信度层只对"信息缺失"题打分
- [ ] 没有"部分正确""基本满足"等模糊表述
- [ ] 权重总和为 100%
- [ ] 每个二级维度都有对应的打分规则

## 第六步：生成 Case 样例

### 需要什么

第五步的打分规则 + 二级维度设计。

### 做什么

每个一级维度生成 1~2 道样例题，总数 5~8 道。每道题要展示它触发了哪些二级维度。

#### 样例题结构

```
【题目ID】      DEMOxx
【难度档位】    Easy / Medium / Hard
【所属维度】    主要考察哪个一级维度（可同时触发多个）
【触发二级维度】 本题考察了哪些二级维度
【输入描述】    精确到关键信息点级别
【用户 query】
【关键信息点】
【约束条件】
【信息缺失标记】

【好答案示例】  2 分答案（完整展示）
【坏答案示例】  0 分答案（展示典型失败模式）
【打分说明】    对照规则解释为什么这么打分，逐个二级维度说明
```

#### 生成要求

**好答案：**
- 满足该题所有触发的二级维度的 2 分标准
- 语言自然，不像模板
- 涉及可信度层时，必须同时"指出缺失" + "给出方向"

**坏答案：**
- 必须是模型真实会犯的错误，不是随机乱答
- "看起来像对的"——流畅、自信、逻辑自洽，但底层判断错
- 对应四种失败模式之一：
  - 字符混淆：把 A 看成 B
  - 答域偏移：回答了另一个问题
  - 约束遗漏：漏掉了一个限制条件
  - 过度自信：对不确定的事给出确定答案

**数量要求：**
- 每个一级维度至少 1 道
- 至少 1 道 Hard 题同时触发 3+ 个一级维度
- 总数 5~8 道

### 自检

- [ ] 坏答案"看起来合理但实际错了"，不是明显乱答
- [ ] 好坏答案的差距能通过打分规则客观区分
- [ ] Hard 题同时触发多个维度
- [ ] 输入描述精确到关键信息点级别
- [ ] 打分说明逐个二级维度解释

## 输出质量标准

最终输出的评测方案必须通过以下检查：

**完整性：**
- [ ] 三个构建原则都有定义 + 做法 + case
- [ ] 4~6 个一级维度均有明确的层次标签，不重复
- [ ] 每个一级维度拆了 2~4 个二级维度
- [ ] 每个二级维度有评判标准 + 拆分理由
- [ ] 每个二级维度有可执行的打分规则
- [ ] 5~8 道 case 样例，覆盖所有一级维度

**可操作性：**
- [ ] 打分规则可直接交给标注员执行，不需二次解释
- [ ] 没有"部分正确""基本满足"等模糊表述
- [ ] 好坏答案的差距能用打分规则客观区分

**逻辑一致性：**
- [ ] 构建原则和评测维度没有混在一起
- [ ] 一级维度之间不交叉（层次标签 + 检验问句均不同）
- [ ] 同一级维度下的二级维度之间不交叉
- [ ] 难度分档有明确标准（三条件定义）
- [ ] 权重总和为 100%

**实用性：**
- [ ] 方案可直接用于指导标注团队工作
- [ ] case 样例中的坏答案是模型真实会犯的错误
- [ ] 信息缺失部分已明确标注，不掩盖不确定性

## 常见错误速查

| 错误 | 症状 | 修正 |
|------|------|------|
| 假设代替追问 | 信息不足时自行假设 | A1/B2 缺失必须问 |
| 原则混入维度 | "我们选了冷门库"出现在维度里 | 移到构建原则，维度只保留"考察能力" |
| 维度交叉 | 两个维度用同一个检验问句 | 找到真正不同的点，放进定义第一句 |
| 打分模糊 | "部分正确""基本满足" | 用可数单位替代，或给明确判断信号 |
| 缺失败模式 | case 只描述了输入，没说为什么出错 | 补充"模型会把XX解释成YY，导致ZZ" |
| 难度无标准 | Hard = "比较难" | 用三条件同时满足定义 |
| 坏答案太假 | 明显乱答，不像真实模型错误 | 对应真实失败模式，看起来合理但底层错 |
| 权重不归一 | 四项权重加起来不是 100% | 按项目调整后确保总和为 100% |
| 维度强套四层 | 不适合的项目也硬用感知/理解/执行/可信度 | 可自定义层次标签，但必须满足三条规则 |
| 二级维度太笼统 | "回答质量好不好"当二级维度 | 落到可数、可观测的粒度 |
| 二级维度交叉 | 两个二级维度判断依据相似 | 找到真正不同的考察侧面 |
| 拆分理由缺失 | 只给了二级维度名称，没解释为什么 | 每个都要有"单独考察的理由"和"不拆分的问题" |
