# 评测集设计框架

将评测项目信息转化为三件套输出：
1. 数据集构建三原则（数据集长什么样）
2. 4~6 个评测维度 + 打分规则（怎么打分）
3. 5~8 道 case 样例（好答案 vs 坏答案）

---

## 第一步：收集输入信息

### 需要什么

**必填（缺一不可）：**

| 编号 | 问题 | 说明 |
|------|------|------|
| A1 | 评测什么能力？ | 一句话描述 |
| A2 | 被评测对象？ | 模型/系统名称 |
| A3 | 评测结果用途？ | 内部研究 / 产品决策 / 模型选型 |
| B1 | 数据怎么来的？ | 线上打捞 / 手工构造 / 爬取 / 合成 |
| B2 | 数据覆盖的时间范围？ | 影响 case 时间锚点，必须有 |
| B3 | 数据规模？ | 大概多少题 |

**选填（有则更好）：**

| 编号 | 问题 |
|------|------|
| C1 | 最难的地方是什么？ |
| C2 | 模型最容易在哪出错？ |
| D1 | 人工标注 / 模型打分 / 混合？ |
| D2 | 专职标注员还是出题人自己标？ |
| E1 | 已有维度草稿 |
| E2 | 已有 case 例子 |
| E3 | 对标行业评测集 |

### 怎么收集

**三条铁律：**
1. 对话里已出现的信息直接用，不重复问
2. A1 和 B2 缺失时必须问，不能假设后继续——这是最严重的错误
3. 先一次性列出所有待确认问题，再按优先级渐进追问

**追问优先级：**
- P1（没有不能继续）：A1、B2
- P2（强烈建议）：A3、B1、C2、D1
- P3（有更好）：C1、D2、E1~E3

P1 用户说"不清楚"→ 引导推导，不能跳过。
P2/P3 用户说"不清楚"→ 标注"待确认"后继续。

### 输出

一份结构化的项目信息摘要，标注哪些已确认、哪些待确认。

## 第二步：推导数据集构建三原则

### 需要什么

第一步收集的项目信息。

### 做什么

按固定框架推导三个原则。**框架固定，内容随项目变化。**

```
原则一：模型陌生的     → 规避记忆优势，测真实泛化
原则二：种类足够丰富   → 保证覆盖面，结论普适
原则三：有明确难度梯度 → 画出能力曲线，而不只是一个总分
```

**每个原则输出三样东西：**
1. 一句话定义：解决什么问题
2. 具体做法：数据集怎么操作
3. 2~3 个具体 case：必须有时间锚点 + 真实库/API 名 + 失败模式

**各原则要点：**

原则一（模型陌生的）：
- case 时间必须在项目启动之后，训练截止之前的内容无效
- 指向真实存在的库/API，不编造
- 说清楚"模型为什么会在出错"的具体机制

原则二（种类足够丰富）：
- 在三个子维度上展开：输入类型、问题类型、领域类型
- 每个子维度举 2~3 个例子

原则三（有难度梯度）：
- Easy：单一信息源 + 单步推断
- Medium：多信息源 + 两步推断
- Hard：多约束 + 多步推断 + 信息缺口（三个条件同时满足）
- 难度分档的价值：不是让题有难有易，而是画出能力曲线

### 自检

- [ ] 三个原则描述的是"数据集长什么样"，不是"模型能力如何"
- [ ] 每个原则有 2~3 个带时间锚点的 case
- [ ] case 中的库名、API 名、时间真实存在，没编造

## 第三步：设计评测维度

### 需要什么

第二步的构建原则 + 项目信息。

### 做什么

设计 4~6 个评测维度，每个维度必须满足三条规则：

**规则一：每个维度有唯一的"考察层次"标签**

```
感知层   → 读没读对？    （模型能不能读准输入信息）
理解层   → 问没问对？    （模型能不能理解用户意图）
执行层   → 条件全满足？  （模型能不能按要求完成任务）
可信度层 → 知不知道不确定？（模型知不知道自己的推断边界）
```

两个维度如果用同一个层次标签 → 有交叉，必须合并或重新定义。

**规则二：每个维度用一个独立问句检验**

如果两个维度的检验问句高度相似 → 它们在测同一件事，需要合并。

**规则三：构建原则 ≠ 评测维度**

判断标准：
- "我们选了哪类数据" → 构建原则，不是维度
- "我们考察模型什么能力" → 维度

如果维度描述里出现大量"我们选了…""我们覆盖了…" → 构建原则混进来了，剥离。

**维度数量参考：**
- 单模态单任务：4 个
- 多模态或多任务：5 个
- 多模态 + 多任务 + 多约束：6 个

### 标准维度池（按需选用）

| 维度 | 层次 | 适用场景 |
|------|------|----------|
| 输入信息提取准确性 | 感知层 | 视觉/文档输入 |
| 用户意图理解与对齐 | 理解层 | 问答类评测 |
| 复杂约束遵循度 | 执行层 | 多条件任务 |
| 回答的边界意识 | 可信度层 | 信息可能不完整 |
| 多步推理连贯性 | 执行层 | 链式推断 |
| 跨域知识迁移稳定性 | 理解层 | 多语言/多领域 |

### 自检

- [ ] 每个维度有明确的考察层次标签，且不重复
- [ ] 相邻维度的检验问句不同
- [ ] 维度描述里没有"我们选了…"这类构建原则的内容

## 第四步：生成打分规则

### 需要什么

第三步的维度设计。

### 做什么

为每个维度编写可操作的打分规则。核心要求：**标注员不靠主观判断，直接执行。**

#### 出题表模板（每道题必填）

```
【题目ID】
【输入描述】
【用户问题】
【参考答案】
【关键信息点清单】（编号列出）
【约束条件列表】（编号列出，无则填"无"）
【信息缺失标记】（是/否）
【难度档位】Easy / Medium / Hard
```

#### 打分规则速查表

按层次选择对应模板，根据项目填充具体规则：

**感知层 — 逐条核查信息点**
```
最小单位：关键信息点（可数）
结果：✓ 正确（与原始一致） / ✗ 错误（不一致或未提及）
得分：正确数 / 总数
```

**理解层 — 整题三档**
```
2分：区域对齐正确 + 问题类型识别正确
1分：一对一错
0分：两个都错，或与输入无关
边界：与输入有实质关联，最低 1 分
```

**执行层 — 逐条核查约束**
```
最小单位：约束条件（可数）
结果：✓ 满足(1) / △ 部分满足(0.5，仅可量化约束) / ✗ 违反(0)
得分：(满足数 + 部分满足数×0.5) / 总约束数
区分：硬约束（只有✓/✗）vs 软约束（允许△）
```

**可信度层 — 仅对信息缺失题打分**
```
触发：信息缺失标记=是 的题才打分，其余默认满分
2分：指出缺失 + 说明影响 + 给方向性推断
1分：识别到不足但模糊，或直接拒答
0分：未识别不足就给确定性答案
0分信号："一定是""肯定是""就是因为" + 指向缺失部分
```

#### 权重分配参考

```
感知层：15~20%（基础门槛）
理解层：25~30%（核心）
执行层：25~30%（核心）
可信度层：15~20%（拔高）
```

### 自检

- [ ] 感知层和执行层的打分单位是"可数的"（信息点数、约束数）
- [ ] 理解层有明确的 0/1/2 分判断边界
- [ ] 可信度层只对"信息缺失"题打分
- [ ] 没有"部分正确""基本满足"等模糊表述

## 第五步：生成 Case 样例

### 需要什么

第四步的打分规则 + 维度设计。

### 做什么

每个维度生成 1~2 道样例题，总数 5~8 道。

#### 样例题结构

```
【题目ID】      DEMOxx
【难度档位】    Easy / Medium / Hard
【所属维度】    主要考察哪个维度（可同时触发多个）
【输入描述】    精确到关键信息点级别
【用户 query】
【关键信息点】
【约束条件】
【信息缺失标记】

【好答案示例】  2 分答案（完整展示）
【坏答案示例】  0 分答案（展示典型失败模式）
【打分说明】    对照规则解释为什么这么打分
```

#### 生成要求

**好答案：**
- 满足该题所有维度的 2 分标准
- 语言自然，不像模板
- 涉及可信度层时，必须同时"指出缺失" + "给出方向"

**坏答案：**
- 必须是模型真实会犯的错误，不是随机乱答
- "看起来像对的"——流畅、自信、逻辑自洽，但底层判断错
- 对应四种失败模式之一：
  - 字符混淆：把 A 看成 B
  - 答域偏移：回答了另一个问题
  - 约束遗漏：漏掉了一个限制条件
  - 过度自信：对不确定的事给出确定答案

**数量要求：**
- 每个维度至少 1 道
- 至少 1 道 Hard 题同时触发 3+ 个维度
- 总数 5~8 道

### 自检

- [ ] 坏答案"看起来合理但实际错了"，不是明显乱答
- [ ] 好坏答案的差距能通过打分规则客观区分
- [ ] Hard 题同时触发多个维度
- [ ] 输入描述精确到关键信息点级别

## 常见错误速查

| 错误 | 症状 | 修正 |
|------|------|------|
| 假设代替追问 | 信息不足时自行假设 | A1/B2 缺失必须问 |
| 原则混入维度 | "我们选了冷门库"出现在维度里 | 移到构建原则，维度只保留"考察能力" |
| 维度交叉 | 两个维度用同一个检验问句 | 找到真正不同的点，放进定义第一句 |
| 打分模糊 | "部分正确""基本满足" | 用可数单位替代，或给明确判断信号 |
| 缺失败模式 | case 只描述了输入，没说为什么出错 | 补充"模型会把XX解释成YY，导致ZZ" |
| 难度无标准 | Hard = "比较难" | 用三条件同时满足定义 |
| 坏答案太假 | 明显乱答，不像真实模型错误 | 对应真实失败模式，看起来合理但底层错 |
