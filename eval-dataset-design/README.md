# eval-dataset-design

一套 AI 模型评测集设计的结构化方法论。输入项目背景信息，输出可直接交给标注团队执行的完整评测方案——包括构建原则、评测维度、打分规则和 case 样例。

> 不是理论框架，是可以直接用的流程。每一步都有输入/输出/自检，踩过的坑都列在常见错误表里。

---

## 解决什么问题

做过评测集的人大概率遇到过这三个坑：

**坑一：构建原则和评测维度搞混**
> "我们选了冷门库的代码来测" —— 这是数据集长什么样（构建原则），不是考察模型什么能力（评测维度）。混在一起会导致维度定义模糊，标注员不知道在评什么。

**坑二：打分靠标注员主观判断**
> "部分正确给一半分" "基本满足算过" —— 每个标注员对"部分"和"基本"的理解不同，标注一致性直接崩掉。

**坑三：难度分档没有标准**
> Hard 的定义是"比较难的题" —— 这等于没定义。出题人觉得难的，标注员可能觉得简单。

这个框架用五步流程系统性地解决这三个问题。

## 工作流程

```
输入：项目背景信息
  │
  ▼
┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│  收集信息    │ ──▶ │  构建原则    │ ──▶ │  评测维度    │
│  确认缺口    │     │  三个原则    │     │  4~6 个维度  │
└─────────────┘     └─────────────┘     └─────────────┘
                                               │
                                               ▼
                    ┌─────────────┐     ┌─────────────┐
                    │  Case 样例   │ ◀── │  打分规则    │
                    │  5~8 道题    │     │  可执行模板  │
                    └─────────────┘     └─────────────┘
                          │
                          ▼
                    输出：完整评测方案
```

五步各自独立，每步格式统一：**需要什么 → 做什么 → 自检**。

## 输入 → 输出示例

**你告诉框架：**

```
评测什么：多模态大模型生成的食物图片质量
被评测对象：GPT-4o / Sora / MidJourney / 可灵 / 即梦
数据来源：韩国首尔真实外卖订单的菜品照片，2025年1-6月，500题
用途：内部模型选型
难点：韩餐/中餐/西餐的"好看"标准不一样
```

**框架输出：**

构建三原则：
```
原则一：模型陌生的
  → 用2025年新出的菜品摄影趋势做数据
  → Case: 韩式"一人食"摆盘风格，模型容易生成传统大桌聚餐构图

原则二：种类足够丰富
  → 输入类型：俯拍/侧拍/特写
  → 问题类型：整体美感/细节真实度/商业可用性
  → 领域类型：韩餐/中餐/西餐各有不同审美标准

原则三：有难度梯度
  → Easy: 单张照片判断好不好看
  → Medium: 同一菜品多角度选最佳封面
  → Hard: 给定品牌调性+菜系特征+商业要求，综合判断
```

评测维度：
```
维度一：视觉信息提取准确性（感知层）→ 读没读对？
  菜品颜色/摆盘/餐具是否和输入描述一致
  打分：逐条核查关键信息点，可数的

维度二：菜系审美对齐度（理解层）→ 问没问对？
  韩餐要有韩餐的样子，不能拍成西餐
  打分：0/1/2 三档

维度三：商业可用性（执行层）→ 条件全满足？
  外卖平台的尺寸、构图、文字留白等硬性要求
  打分：逐条约束核查，区分硬约束和软约束

维度四：生成边界意识（可信度层）→ 知不知道不确定？
  输入信息不够时，模型是瞎猜还是提示补充
  打分：只对信息缺失的题打分
```

## 核心设计理念

### 两层分离

| 层次 | 关注点 | 典型问题 |
|------|--------|----------|
| 构建原则 | 数据质量 | 选什么数据？覆盖什么范围？ |
| 评测维度 | 评分标准 | 用什么维度打分？每个维度怎么判？ |

这两层解决的是不同问题，混在一起是评测集设计最常见的错误。

### 四层递进维度

```
感知层   → 读没读对？      模型能不能读准输入信息
理解层   → 问没问对？      模型能不能理解用户意图
执行层   → 条件全满足？    模型能不能按要求完成任务
可信度层 → 知不知道不确定？ 模型知不知道自己的推断边界
```

每个维度必须有唯一的层次标签。两个维度如果用同一个标签，说明有交叉，需要合并。

### 打分可操作化

| 层次 | 打分方式 | 核心原则 |
|------|----------|----------|
| 感知层 | 信息点逐条核查 | 可数的，不靠判断 |
| 理解层 | 0/1/2 三档 | 有明确的分档边界 |
| 执行层 | 约束逐条核查 | 区分硬约束和软约束 |
| 可信度层 | 仅信息缺失题打分 | 有明确的 0 分信号 |

## 适用场景

- 正在设计评测集，需要系统化方法论
- 已有评测数据但维度混乱、打分标准不统一
- 需要向团队解释评测集的设计逻辑
- 想把评测经验沉淀为可复用的框架
- 多个评测项目需要统一的标准化流程

这是 [Hermes Agent](https://github.com/NousResearch/hermes-agent) 的 Skill 文件。

```bash

mkdir -p <your-project>/.hermes/skills/eval-dataset-design/
```
